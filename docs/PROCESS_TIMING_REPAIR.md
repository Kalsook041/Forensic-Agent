# 进程时序测试修复（2026-10-15）

## 问题与依据

此前完整回归为 119 passed / 2 failed / 1 skipped，两项失败随后单独诊断仍失败。原记录保留在 `local-state/process-timing-diagnostic.xml`，没有删除或改写。

两项测试将 Python 启动、模块导入、受限代理和子进程创建全部包含在 0.25/0.5 秒总预算内，却要求超时之前进程树必已建立。生产执行器本来就从启动开始计时，提前终止尚未完成启动的进程符合总预算约束。既有独立观测中，简单启动约 0.187 秒，代理加父子进程正常退出约 0.485 秒；后者已接近原测试预算。使用 2 秒诊断预算时超时及正常退出路径都没有遗留子进程或线程。记录见 `local-state/process-timing-observations.json`。这些是本机观测，不是所有机器的启动耗时保证。

## 修复与验收

仅修改 `tests/conftest.py`、`tests/test_boundaries.py`、`tests/test_process_review.py`：

- 树清理场景使用 2 秒测试预算，子进程写出自己的 PID 后父进程才输出 started；保留 started、预期停止原因及文件无残留断言，继续要求执行在 3 秒内结束。
- 用 Windows SYNCHRONIZE 句柄及 WaitForSingleObject 检查实际子进程已退出。只将 ERROR_INVALID_PARAMETER 视为 PID 已不存在；权限失败等其他错误不能算通过。
- PID 就绪文件采用写临时文件后替换的方式，避免读取未完成的 PID。显式 Job 场景在调用者关闭 Job 句柄之前核验退出，防止句柄关闭顺带清理而掩盖执行器缺陷。
- 正常父进程退出和超时两条路径都核验子进程退出，并保留无新增读写线程断言。
- 独立保留 0.25 秒总预算终止测试，不要求用户代码必已启动；原 0.3 秒大 stdin 写入超时测试不变。
- 增加存活进程负对照，必须识别并拒绝仍存活的进程，再由测试 finally 清理自己的进程。

生产代码、工具白名单、Shell 边界、Job 限制和超时设置均未修改。27 个 wheel 摘要及 30 个 Python 模块在源码、离线包与本机安装之间保持一致，因此本轮不重建未发生变化的运行包。
